# Platform requirements and enablement

The supported release target is Linux x86_64, Python 3.12, Harbor 0.24.0, and the two OpenSandbox execd protocols. Supporting the Python API does not establish that a particular sandbox deployment satisfies the security contract. This page is for whoever operates the sandbox platform: what must always be enabled, which features are switched on per deployment, and how each is verified. Setup steps are in the [deployment guide](Deployment.md); field reference in [Configuration](Configuration.md).

## Baseline: required on every deployment

- **Lifecycle API.** Server root with `/v1`; create, get, list by label, delete, and TTL renewal for sandboxes. Create must accept the common top-level `networkPolicy` field and the managed create fields (image digest, entrypoint, metadata, timeout, resource limits, volumes, env); policy replacement uses `PUT /v1/sandboxes/{id}/networkpolicy` on upstream OpenSandbox and platforms implementing its compatibility route. Acceptance: create/get/list/delete consistency, list visibility latency, bounded requests, renewable TTL, uncertain-create reconciliation.
- **Exec daemon.** One exec daemon per sandbox, reachable through the platform's sandbox proxy route on the daemon's port (declare an explicit port in `opensandbox.create_fields` when the platform requires it). The daemon runs as root so it can initialize the sandbox and apply each command's numeric identity. Exactly one protocol is selected in `[opensandbox.execd]` — `current` (argv plus numeric identity fields) or `legacy` (quoted command string) — with no fallback between them. The command stream is SSE with per-command IDs; HTTP 409 `CONFLICT` on the command stream is the deployment's explicit busy rejection. Acceptance: identity (uid/gid/cwd/env), nonzero and signal exits, bounded output, background processes, cancellation at every request/delivery stage, a client deadline plus confirmed remote stop of the process group, and unknown status invalidating the environment.
- **Shared storage.** A dedicated shared root that every sandbox worker and the anchor can mount: a host path backed by the same storage on every worker, or an existing RWX PVC with a subpath root. Instances receive only their declared mounts; missing subpaths are created on demand; undeclared volumes must not be auto-mounted. Acceptance: same data on every worker, read-only mounts, subpath isolation, no unintended mounts, binary transfers with original uid/gid/mode including special permission bits.
- **Image registry.** An image registry reachable from both the preparation machine (Docker with BuildKit/buildx) and the sandbox workers, with digest-pinned pulls and linux/amd64 selection. Acceptance: build and runtime pull access tested independently; missing supported architectures are rejected.
- **Share release and anchor.** Flotilla publishes an immutable BusyBox share under the shared root and mounts it at `/.flotilla/bin/busybox`. The digest-pinned anchor image runs BusyBox with `stat`, shell, file-management, and networking applets for directory management, numeric metadata, renewal, and cleanup audits. See the [deployment guide](Deployment.md).
- **Quotas and labels.** Sandbox labels (bounded length) for ownership and reconciliation; instance/TTL quotas at least matching the client's `[limits]` and `[reaper]` budgets, including the anchor instance and startup replacement capacity. Acceptance: actual cgroup limits and quota behavior for requested resources.

## Feature enablement matrix

Each feature below is off until the deployment provides it, the configuration selects it, and the capability report carries evidence. Only a schema-2 `passed` check enables its measured scope; manual declarations are not supported.

| Feature | Platform must provide | Selected in | Evidence and gating | Verify |
|---|---|---|---|---|
| Service peer links | Exact pairwise allow between linked services, via raw peer-IP/CIDR policy targets or `sandbox:<id>` identity targets — behaviorally enforced, not merely accepted by the API | `opensandbox.network.link = "cidr"` (needs `sandbox_cidrs`) or `"sandbox"` | Capabilities `link`, `link_max_members`; `external="any"` is unavailable with `link = "sandbox"` | `python -m tests.contract.foreground` (three mutually reachable services); [network validation](Network_Validation.md) |
| Co-scheduling groups (optional) | Place all instances of one environment in one scheduling group | `opensandbox.group_extension` (only if the deployment implements it) | Extension recorded with capability evidence | Observe group placement of a multi-service run |
| Inbound isolation | Either platform-level default-deny between tenants, or identity-based sandbox ingress rules (initial deny `sandbox:any`, linked peers excepted) | `opensandbox.network.ingress = "deployment"` or `"sandbox"` (the latter requires `link = "sandbox"`) | `inbound_isolation` from independent TCP/UDP controls; a config selector cannot grant `sandbox_ingress`; blocks startup unless present or waived | Independent source with verified outbound access: positive control reachable, isolated target denied |
| Offline (`no-network`) tasks | Egress `defaultAction=deny` with no external rules, where the only tolerated implicit egress is the observed cluster DNS on TCP/UDP 53 | `[network]` external `none`; `[probe]` controlled targets and DNS query name | `network_acceptance` and `external_none` both passed; `supports_no_network` permits measured cluster DNS, not complete disconnection. Resolver non-53 controls are optional diagnostics; known non-DNS implicit egress is still rejected | Negative/positive connectivity controls; [network validation](Network_Validation.md) |
| External egress allowlist / any | Egress policy compilation to none, an allowlist (IPs, CIDRs, host names), or `any` | `[network] external`; `platform_cidrs` required for `any` with `link = "cidr"` | `external_forms`; `any` never covers sandbox ranges or excluded platform ranges | Allowed destinations reachable, disallowed fail |
| Read-only root filesystem and native tmpfs | The internal lifecycle filesystem dialect: create-time `readOnlyRootFilesystem` and `tmpfsMounts`, effective-configuration checks, no inherited template overrides | `opensandbox.filesystem_protocol = "sandbox-system-v1"` (default `"upstream"` sends no fields and rejects such tasks) | `readonly_rootfs` / `native_tmpfs` with passed evidence | `flotilla probe` automatically tests the explicitly selected filesystem dialect; `python -m tests.contract.filesystem`; [filesystem support](Readonly_Rootfs_and_Tmpfs.md) |
| Shared memory size (`shm_size`) | Per-instance `/dev/shm` capacity, enforced by the mounted tmpfs | `opensandbox.filesystem_protocol = "sandbox-system-v1"` (sends `extensions["sandbox-system.io/shm-size"]`; upstream rejects such tasks) | `shm_size` with passed evidence | `flotilla probe` automatically tests explicit shm-size support; [shared memory](Readonly_Rootfs_and_Tmpfs.md#shared-memory-shm_size) |
| Non-root task images | The root exec daemon above, plus registry space for a small derived runtime image (`USER 0:0`) built by the preparation machine | `[build] target` (builder required; default-root images need no extra build) | Covered by baseline exec acceptance | Run a task whose image declares a non-root `USER`; service startup, healthchecks, and default exec keep the original numeric identity |
| UDP between services | UDP policy enforcement between linked peers, in addition to TCP | Same selectors as peer links | Capability `link_udp`; do not infer it from TCP evidence | UDP content transfer between services (measured independently, not inferred from TCP) |
| Host devices (`/dev/kvm`, `/dev/net/tun`) | The privileged runtime exposes the device node to root when the create request carries the device extension; TUN also needs `CAP_NET_ADMIN` in the sandbox network namespace | `opensandbox.privileged_extensions` selects a runtime that can host them (e.g. `runtimeClassName = "sysbox-runc"`); Flotilla adds `kvm`/`tun` = `"true"` per instance | `runtime.kvm` / `runtime.tun` passed with privileged scope, on top of passed privileged runtime evidence | The privileged probe phase creates one instance per device: KVM API version 12 and `KVM_CREATE_VM`; TAP interface creation |

Rejected before any sandbox is created, with a field path: devices other than `/dev/kvm` and `/dev/net/tun`, extra hosts, pid/ipc sharing, GPU, and other unsupported Compose keys (see [Compose support](Compose_Support.md)). `privileged: true` services are admitted only with the `privileged_runtime` capability, and services declaring `/dev/kvm` or `/dev/net/tun` only when the report's `devices` includes them.

## Evidence and scope

`capabilities.json` is generated by probe from `deployment.toml`. Each check records one outcome (`passed`, `failed`, `skipped`, `error`), concise evidence, measurements and scope. Missing prerequisites and failed positive controls cannot become isolation success. Report schema 1 is rejected; historical measurements or declarations are not imported into schema 2.

Evidence binds backend/endpoint/project, ordinary and privileged runtime choices, execd/filesystem protocols, network implementation/policy, storage mapping and shared-tool release. Build image replacements and preparation concurrency do not invalidate unrelated runtime evidence. A fingerprint mismatch rejects the report; matching the endpoint alone is insufficient.

Probe checks configured anchor/trial TTLs and actual expiry changes on renewal. It reports observed group size and list latency, not maximum TTL, maximum group size, or guaranteed future latency. GC retains its configured visibility budget. Two-instance storage visibility is not all-node validation; operators must ensure the shared root is provisioned on every worker.

Privileged evidence covers the configured create mapping, separately measured storage/auth/network behavior and confirmed outer deletion; this isolation evidence admits `privileged: true` services. The Docker daemon and digest-pinned inner execution/resource limits are measured when `probe.inner_image` is set and recorded in `runtime.privileged_runtime`, but are not required. Devices need the isolation evidence and their own device check. It does not establish arbitrary Linux privileges. FUSE requires the configured extension and actual local mount/read/write/unmount. KVM and TUN are measured on their own privileged instances that request only that device; a failure leaves the other device and the privileged runtime unaffected. Kata does not imply KVM; no automatic switch to sysbox occurs. Unsupported privileged filesystem combinations remain forbidden.

Missing required execution/storage/lifecycle/network acceptance blocks startup. The three explicit security waivers remain `inbound_isolation`, `exec_auth`, and `no_auto_mount`; they do not implement protection or rewrite failed checks. They also do not waive missing critical network controls. Keep private reports out of version control and review candidate cleanup results before promotion.

Older upstream/internal acceptance runs describe their own code, images, configuration and time. They do not establish current schema-2 capabilities. This implementation's offline regressions are not real sandbox acceptance.

## Formal release gates

Both `current` and `legacy` must independently pass source preparation, foreground/background execution, timeout and repeated cancellation, binary transfer, service networking, and cleanup checks. Run with an independent observer to verify instances and owned directories disappear. Also verify real Docker archive metadata, prepare/cleanup saturation, and a prolonged renewal/cleanup workload.

Pass unit tests from a clean checkout and extracted source archive, base wheel installation without Harbor, and the Harbor extra. Inspect the release commit, wheel, sdist, and image contexts for private material and excluded modules. Any change after acceptance must repeat the affected checks before the release is tagged; see [RELEASING.md](../RELEASING.md).
