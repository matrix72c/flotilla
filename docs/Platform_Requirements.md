# Platform requirements and enablement

The supported release target is Linux x86_64, Python 3.12, Harbor 0.24.0, and the two OpenSandbox execd protocols. Supporting the Python API does not establish that a particular sandbox deployment satisfies the security contract. This page is for whoever operates the sandbox platform: what must always be enabled, which features are switched on per deployment, and how each is verified. Setup steps are in the [deployment guide](Deployment.md); field reference in [Configuration](Configuration.md).

## Baseline: required on every deployment

- **Lifecycle API.** Server root with `/v1`; create, get, list by label, delete, and TTL renewal for sandboxes. Create must accept the common top-level `networkPolicy` field and the managed create fields (image digest, entrypoint, metadata, timeout, resource limits, volumes, env); policy replacement uses `PUT /v1/sandboxes/{id}/networkpolicy` on upstream OpenSandbox and platforms implementing its compatibility route. Acceptance: create/get/list/delete consistency, list visibility latency, bounded requests, renewable TTL, uncertain-create reconciliation.
- **Exec daemon.** One exec daemon per sandbox, reachable through the platform's sandbox proxy route on the daemon's port (declare an explicit port in `opensandbox.create_fields` when the platform requires it). The daemon runs as root so it can initialize the sandbox and apply each command's numeric identity. Exactly one protocol is selected in `[opensandbox.execd]` — `current` (argv plus numeric identity fields) or `legacy` (quoted command string) — with no fallback between them. The command stream is SSE with per-command IDs; HTTP 409 `CONFLICT` on the command stream is the deployment's explicit busy rejection. Acceptance: identity (uid/gid/cwd/env), nonzero and signal exits, bounded output, background processes, cancellation at every request/delivery stage, a client deadline plus confirmed remote stop of the process group, and unknown status invalidating the environment.
- **Shared storage.** A dedicated shared root that every sandbox worker and the anchor can mount: a host path backed by the same storage on every worker, or an existing RWX PVC with a subpath root. Instances receive only their declared mounts; missing subpaths are created on demand; undeclared volumes must not be auto-mounted. Acceptance: same data on every worker, read-only mounts, subpath isolation, no unintended mounts, binary transfers with original uid/gid/mode including special permission bits.
- **Image registry.** An image registry reachable from both the preparation machine (Docker with BuildKit/buildx) and the sandbox workers, with digest-pinned pulls and linux/amd64 selection. Acceptance: build and runtime pull access tested independently; missing supported architectures are rejected.
- **Share release and anchor.** Flotilla publishes an immutable BusyBox share under the shared root and mounts it at `/.flotilla/bin/busybox`. The digest-pinned anchor image runs BusyBox with `stat`, shell, file-management, and networking applets for directory management, numeric metadata, renewal, and cleanup audits. See the [deployment guide](Deployment.md).
- **Quotas and labels.** Sandbox labels (bounded length) for ownership and reconciliation; instance/TTL quotas at least matching the client's `[limits]` and `[reaper]` budgets, including the anchor instance and startup replacement capacity. Acceptance: actual cgroup limits and quota behavior for requested resources.

## Feature enablement matrix

Each feature below is off until the deployment provides it, the configuration selects it, and the capability report carries evidence. A declared item is an operator assertion, not an automatic test result.

| Feature | Platform must provide | Selected / declared in | Evidence and gating | Verify |
|---|---|---|---|---|
| Service peer links | Exact pairwise allow between linked services, via raw peer-IP/CIDR policy targets or `sandbox:<id>` identity targets — behaviorally enforced, not merely accepted by the API | `opensandbox.network.link = "cidr"` (needs `sandbox_cidrs`) or `"sandbox"` | Capabilities `link`, `link_max_members`; `external="any"` is unavailable with `link = "sandbox"` | `python -m tests.contract.foreground` (three mutually reachable services); [network validation](Network_Validation.md) |
| Co-scheduling groups (optional) | Place all instances of one environment in one scheduling group | `opensandbox.group_extension` (only if the deployment implements it) | Extension recorded with capability evidence | Observe group placement of a multi-service run |
| Inbound isolation | Either platform-level default-deny between tenants, or identity-based sandbox ingress rules (initial deny `sandbox:any`, linked peers excepted) | `opensandbox.network.ingress = "deployment"` or `"sandbox"` (the latter requires `link = "sandbox"`) | `inbound_isolation` (declared, never inferred) or `sandbox_ingress`; blocks startup unless present or waived | Independent source with verified outbound access: positive control reachable, isolated target denied |
| Offline (`no-network`) tasks | Egress `defaultAction=deny` with no external rules, where the only tolerated implicit egress is the declared cluster DNS on TCP/UDP 53 | `[network]` external `none`; `cluster_dns` plus machine-readable `implicit_egress` in `declared.json` | `external_forms` contains `"none"`; `supports_no_network` — a deployment whose DNS exception is IP-wide (any port) does not qualify | Negative/positive connectivity controls; [network validation](Network_Validation.md) |
| External egress allowlist / any | Egress policy compilation to none, an allowlist (IPs, CIDRs, host names), or `any` | `[network] external`; `platform_cidrs` required for `any` with `link = "cidr"` | `external_forms`; `any` never covers sandbox ranges or excluded platform ranges | Allowed destinations reachable, disallowed fail |
| Read-only root filesystem and native tmpfs | The internal lifecycle filesystem dialect: create-time `readOnlyRootFilesystem` and `tmpfsMounts`, effective-configuration checks, no inherited template overrides | `opensandbox.filesystem_protocol = "sandbox-system-v1"` (default `"upstream"` sends no fields and rejects such tasks) | `readonly_rootfs` / `native_tmpfs` with `probed` evidence and a matching `filesystem_profile` fingerprint | `flotilla probe` with `probe_readonly_rootfs`/`probe_native_tmpfs`; `python -m tests.contract.filesystem`; [filesystem support](Readonly_Rootfs_and_Tmpfs.md) |
| Non-root task images | The root exec daemon above, plus registry space for a small derived runtime image (`USER 0:0`) built by the preparation machine | `[build] target` (builder required; default-root images need no extra build) | Covered by baseline exec acceptance | Run a task whose image declares a non-root `USER`; service startup, healthchecks, and default exec keep the original numeric identity |
| UDP between services | UDP policy enforcement between linked peers, in addition to TCP | Same selectors as peer links | Capability `link_udp`; do not infer it from TCP evidence | UDP content transfer between services (included in the foreground contract when declared) |

Rejected before any sandbox is created, with a field path: devices, extra hosts, `on-failure` restarts, pid/ipc sharing, privileged runtime, GPU, and other unsupported Compose keys (see [Compose support](Compose_Support.md)). The report may record `privileged_runtime` and `devices` for evaluation; Flotilla does not use them to admit tasks.

## Verified deployment profiles

Both profiles below were validated end to end; deployment-specific values (endpoints, projects, registries) are kept private with each capability report.

- **Upstream OpenSandbox** (open-source single-node deployment): server/controller 1.2.0-rc.1, execd v1.0.22.1, `legacy` protocol, hostPath shared root, `link = "cidr"` with exact peer allows (TCP and UDP content verified). No default inbound isolation — an explicit `inbound_isolation` waiver is required; the cluster-DNS exception is IP-wide, so offline (`no-network`) tasks are **not** supported. Validated: runtime and queueing, Compose dependencies/healthchecks/restart semantics, build control and recovery, volume seeding and metadata (numeric uid/gid, 6755, nocopy, bind), single-file mounts, service networking, fault recovery without replay, GC and share lifecycle, Harbor oracle/nop with a separate verifier, and independent cleanup audits; 954+963 unit regressions. Open item: occasional slow command-stream requests, under investigation with the platform side; client-side recovery within the check budget is verified.
- **Internal sandbox-system deployment**: `legacy` execd with token authentication, project PVC shared storage with a subpath root, `link`/`ingress = "sandbox"` identity policies with a scheduling-group extension, declared cluster DNS (offline tasks supported), and the `sandbox-system-v1` filesystem dialect with read-only rootfs and native tmpfs passing the 54-check behavioral contract. Also validated at dataset scale: roughly 1.1k tasks across five evaluation datasets, 96 concurrent trials sustained from one client process with confirmed cleanup.

## Evidence

Capability items have a source (`probed` or `declared`) and evidence. A declared item is an operator assertion, not an automatic test result. `probe` measures only its implemented checks; an interrupted or failed probe is not evidence that a capability is absent or present. The example declaration asserts no unverified security capabilities.

The capability report is deployment-specific and must match its endpoint. Keep real reports private. Missing required execution/storage/lifecycle capabilities block startup. Security gaps (`inbound_isolation`, `exec_auth`, `no_auto_mount`) block startup unless explicitly accepted in `security.accept_insecure`; acceptance does not implement the missing protection, and stale waivers warn.

## Formal release gates

Both `current` and `legacy` must independently pass source preparation, foreground/background execution, timeout and repeated cancellation, binary transfer, service networking, and cleanup checks. Run with an independent observer to verify instances and owned directories disappear. Also verify real Docker archive metadata, prepare/cleanup saturation, and a prolonged renewal/cleanup workload.

Pass unit tests from a clean checkout and extracted source archive, base wheel installation without Harbor, and the Harbor extra. Inspect the release commit, wheel, sdist, and image contexts for private material and excluded modules. Any change after acceptance must repeat the affected checks before the release is tagged; see [RELEASING.md](../RELEASING.md).
