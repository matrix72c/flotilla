# Platform requirements and enablement

The supported release target is Linux x86_64, Python 3.12, the two OpenSandbox execd protocols, and — for the optional native Harbor adapter — a patched Harbor build, since stock Harbor 0.24.0 lacks those interfaces. Supporting the Python API does not establish that a particular sandbox deployment satisfies the security contract. This page is for whoever operates the sandbox platform: what must always be enabled, which features are switched on per deployment, and how each is verified. Setup steps are in the [deployment guide](Deployment.md); field reference in [Configuration](Configuration.md).

## Baseline: required on every deployment

- **Lifecycle API.** Server root with `/v1`; create, get, list by label, delete, and TTL renewal for sandboxes. Create must accept the common top-level `networkPolicy` field and the managed create fields (image digest, entrypoint, metadata, timeout, resource limits, volumes, env); policy replacement uses `PUT /v1/sandboxes/{id}/networkpolicy` on upstream OpenSandbox and platforms implementing its compatibility route. Acceptance: create/get/list/delete consistency, list visibility latency, bounded requests, renewable TTL, uncertain-create reconciliation.
- **Exec daemon.** One exec daemon per sandbox, reachable through the platform's sandbox proxy route on the daemon's port (declare an explicit port in `opensandbox.create_fields` when the platform requires it). The daemon runs as root so it can initialize the sandbox and apply each command's numeric identity. Exactly one protocol is selected in `[opensandbox.execd]` — `current` (argv plus numeric identity fields) or `legacy` (quoted command string) — with no fallback between them. The command stream is SSE with per-command IDs; HTTP 409 `CONFLICT` on the command stream is the deployment's explicit busy rejection. Acceptance: identity (uid/gid/cwd/env), nonzero and signal exits, bounded output, background processes, cancellation at every request/delivery stage, a client deadline plus confirmed remote stop of the process group, and unknown status invalidating the environment.
- **Shared storage.** A dedicated shared root that every sandbox worker and the anchor can mount: a host path backed by the same storage on every worker, or an existing RWX PVC with a subpath root. Instances receive only their declared mounts; missing subpaths are created on demand; undeclared volumes must not be auto-mounted. Acceptance: same data on every worker, read-only mounts, subpath isolation, no unintended mounts, binary transfers with original uid/gid/mode including special permission bits.
- **Image registry.** An image registry reachable from both the preparation machine (Docker with BuildKit/buildx) and the sandbox workers, with digest-pinned pulls and linux/amd64 selection. Acceptance: build and runtime pull access tested independently; missing supported architectures are rejected.
- **Share release and anchor.** Flotilla publishes an immutable BusyBox share under the shared root and mounts it read-only at `/.flotilla`, so the binary is at `/.flotilla/bin/busybox`. The digest-pinned anchor image runs BusyBox with `stat`, shell, file-management, and networking applets for directory management, numeric metadata, renewal, and cleanup audits. See the [deployment guide](Deployment.md).
- **Quotas and labels.** Sandbox labels (bounded length) for ownership and reconciliation; instance/TTL quotas at least matching the client's `[limits]` and `[reaper]` budgets, including the anchor instance and startup replacement capacity. Acceptance: actual cgroup limits and quota behavior for requested resources.

## Feature enablement matrix

A feature below is available once the deployment provides it and the configuration selects it. Nothing measures them first: a platform that cannot host a device, a TTL or a tmpfs refuses the create request, and that refusal is a better answer than a report that was accurate last month. Isolation is the exception — a deployment that ignores an egress policy or serves the exec channel without checking the token returns success anyway — so `flotilla probe` measures isolation, and only isolation.

Two kinds of numbers cannot work that way either, because getting one wrong refuses nothing and misbehaves later. Those are declared in `[platform]`: how long a listing may lag (`list_visibility_s`), the largest TTL the platform grants (`max_ttl_s`), the longest label value it stores, the largest link group, the implicit egress a sandbox has anyway, and the cluster DNS addresses behind it.

| Feature | Platform must provide | Selected in | How a missing platform behavior shows up | Verify |
|---|---|---|---|---|
| Service peer links | Exact pairwise allow between linked services, via raw peer-IP/CIDR policy targets or `sandbox:<id>` identity targets — behaviorally enforced, not merely accepted by the API | `opensandbox.network.link = "cidr"` (needs `sandbox_cidrs`) or `"sandbox"` | A task with more members than `platform.link_max_members` is rejected before any create; a platform that accepts the policy without enforcing it is caught by the contract test, not by configuration. `external="any"` is unavailable with `link = "sandbox"` | `python -m tests.contract.foreground` (three mutually reachable services); [network validation](Network_Validation.md) |
| Co-scheduling groups (optional) | Place all instances of one environment in one scheduling group | `opensandbox.group_extension` (only if the deployment implements it) | A platform without the extension refuses the create request carrying it | Observe group placement of a multi-service run |
| Inbound isolation | Either platform-level default-deny between tenants, or identity-based sandbox ingress rules (initial deny `sandbox:any`, linked peers excepted) | `opensandbox.network.ingress = "deployment"` or `"sandbox"` (the latter requires `link = "sandbox"`) | Isolation, so measured: `inbound_isolation` comes from independent TCP/UDP controls, and `flotilla probe` exits nonzero when it does not hold and `security.accept_insecure` does not name it | Independent source with verified outbound access: positive control reachable, isolated target denied |
| Offline (`no-network`) tasks | Egress `defaultAction=deny` with no external rules, where the only tolerated implicit egress is the observed cluster DNS on TCP/UDP 53 | `[network]` external `none`; `[probe]` controlled targets and DNS query name | Isolation, so measured: `external_none` and `network_acceptance` must both hold. `supports_no_network` permits the `platform.cluster_dns` resolvers on TCP/UDP 53, not complete disconnection; declared `platform.implicit_egress` outside that rejects offline tasks | Negative/positive connectivity controls; [network validation](Network_Validation.md) |
| External egress allowlist / any | Egress policy compilation to none, an allowlist (IPs, CIDRs, host names), or `any` | `[network] external`; `platform_cidrs` required for `any` with `link = "cidr"` | Isolation, so measured: the probe allows, denies and re-allows traffic for each form it exercises, and reports which forms it proved. `any` never covers sandbox ranges or excluded platform ranges | Allowed destinations reachable, disallowed fail |
| Read-only root filesystem and native tmpfs | The internal lifecycle filesystem dialect: create-time `readOnlyRootFilesystem` and `tmpfsMounts`, effective-configuration checks, no inherited template overrides | `opensandbox.filesystem_protocol = "sandbox-system-v1"` (default `"upstream"` sends no fields and rejects such tasks) | The `upstream` dialect sends no such fields and rejects the task at planning; a platform that advertises the dialect but drops the fields fails the contract test | `flotilla probe` automatically tests the explicitly selected filesystem dialect; `python -m tests.contract.filesystem`; [filesystem support](Readonly_Rootfs_and_Tmpfs.md) |
| Shared memory size (`shm_size`) | Per-instance `/dev/shm` capacity, enforced by the mounted tmpfs | `opensandbox.filesystem_protocol = "sandbox-system-v1"` (sends `extensions["sandbox-system.io/shm-size"]`; upstream rejects such tasks) | The `upstream` dialect rejects the task at planning; a dropped extension shows up as a `/dev/shm` of the wrong size in the contract test | `flotilla probe` automatically tests explicit shm-size support; [shared memory](Readonly_Rootfs_and_Tmpfs.md#shared-memory-shm_size) |
| UDP between services | UDP policy enforcement between linked peers, in addition to TCP | Same selectors as peer links | A platform that drops UDP rules fails the UDP transfer check; TCP success never implies it | UDP content transfer between services (measured independently, not inferred from TCP) |
| Host devices (`/dev/kvm`, `/dev/net/tun`) | The privileged runtime exposes the device node to root when the create request carries the device extension; TUN also needs `CAP_NET_ADMIN` in the sandbox network namespace | `opensandbox.privileged_extensions` selects a runtime that can host them (e.g. `runtimeClassName = "sysbox-runc"`); Flotilla adds `kvm`/`tun` = `"true"` per instance | A runtime that cannot host the device fails the create request carrying its extension | The privileged probe phase creates one instance per device: KVM API version 12 and `KVM_CREATE_VM`; TAP interface creation |

Rejected before any sandbox is created, with a field path: devices other than `/dev/kvm` and `/dev/net/tun`, extra hosts, pid/ipc sharing, GPU, and other unsupported Compose keys (see [Compose support](Compose_Support.md)). A `privileged: true` service, or one declaring a device, is planned onto the privileged runtime; whether that runtime exists is the platform's answer to the create request.

## Isolation evidence

`flotilla probe` creates real sandboxes against the deployment spec it is given and measures seven isolation properties: `external_none`, `network_acceptance`, `inbound_isolation`, `read_only`, `subdir_isolation`, `no_auto_mount` and `exec_auth`. It prints what each observation was and exits nonzero when one did not hold and `security.accept_insecure` does not name it. Confirmed cleanup is required unconditionally, and cannot be waived: a deployment whose resources are not confirmed deleted is refused.

Nothing is written. The evidence is values in memory for the length of the probe run, so there is no report file, no schema and no version to maintain, and a client in another process has no way to re-derive the observations. That makes the probe an operator step against a deployment, and its exit status the gate — not a file a later startup re-reads and re-checks.

Each restriction is measured by allowing traffic, denying it, and allowing it again. A single blocked exchange proves nothing: it could be a broken target. Missing positive controls and failed restores are reported as not-shown, never as isolation success.

A restriction holding for an ordinary sandbox says nothing about one on the privileged runtime, so the storage, egress, inbound and exec-channel checks run a second time there when `probe.privileged_image` is set. That privileged evidence is what admits a `privileged: true` service; it does not establish arbitrary Linux privileges, and Kata does not imply KVM.

Two-instance storage visibility is not all-node validation; operators must ensure the shared root is provisioned on every worker. Only `inbound_isolation`, `exec_auth` and `no_auto_mount` can be waived — a waiver records that the operator runs without the property, and neither implements it nor claims it was shown.

Offline regressions in this repository are not sandbox acceptance; only a probe against the target deployment is.

## Formal release gates

Both `current` and `legacy` must independently pass source preparation, foreground/background execution, timeout and repeated cancellation, binary transfer, service networking, and cleanup checks. Run with an independent observer to verify instances and owned directories disappear. Also verify real Docker archive metadata, prepare/cleanup saturation, and a prolonged renewal/cleanup workload.

Pass unit tests from a clean checkout and extracted source archive, and from an installed wheel. Inspect the release commit, wheel, sdist, and image contexts for private material and excluded modules. Any change after acceptance must repeat the affected checks before the release is tagged; see [RELEASING.md](../RELEASING.md).
