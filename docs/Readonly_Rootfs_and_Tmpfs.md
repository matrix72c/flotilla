# Read-only root filesystems and native tmpfs

Compose `read_only: true` and `tmpfs` are supported through an explicitly selected lifecycle extension on compatible internal container deployments. They are independent capabilities. A task requiring either capability is rejected when the selected deployment has no matching evidence. Flotilla never retries a create after removing filesystem restrictions, and never substitutes a regular directory for tmpfs.

The internal mapping follows the platform's **17. Sandbox read-only root filesystem and tmpfs memory mounts** contract. Selecting this mapping is not evidence that a particular server or runtime implements it; run the optional probes on the actual deployment.

## Enable a deployment

Add this key to the existing `[opensandbox]` table in the private deployment configuration:

```toml
[opensandbox]
# Keep the existing endpoint, credential_env, capabilities and other settings.
filesystem_protocol = "sandbox-system-v1"
```

This is independent of `[opensandbox.execd].protocol`. The default filesystem protocol is `"upstream"`, which sends neither `readOnlyRootFilesystem` nor `tmpfsMounts`, including for ordinary tasks with false/empty requirements. Upstream mode rejects tasks requiring the new capabilities even if a capability file claims they are available.

Add these optional fields to the existing `declared.json` object:

```json
{
  "probe_readonly_rootfs": true,
  "probe_native_tmpfs": true
}
```

These flags request measurements; they do not assert support. Then regenerate the report with the same configuration that will run tasks:

```sh
flotilla probe --deployment deployment.toml --declared declared.json \
  --image "$PROBE_IMAGE" --out capabilities.json
```

The image must meet the existing probe requirements, contain `/tmp` and `/var/tmp`, and provide `stat` (including `-f`), `dd`, `grep`, and `touch`. The deployment must support the configured share mounts. Both optional flags default to false, so existing probe invocations do not attempt extension requests.

The report records `runtime.readonly_rootfs` and `storage.native_tmpfs`. Only successful `probed` evidence enables these features. A `filesystem_profile` fingerprint binds that evidence to the filesystem dialect, creation fields, and normal/privileged runtime extensions. Changing those settings, or loading an old report without the fingerprint, disables the optional capabilities until reprobed. Existing required capabilities and ordinary tasks remain usable. Use reports generated by the same Flotilla version; older strict readers may reject new optional report fields.

The probes check root writes failing with EROFS, writable-volume file transfer, `/etc/hosts` updates, the actual tmpfs filesystem type, ownership/mode, non-root writes, ENOSPC at a small capacity, contents surviving another exec, stdout/stderr delivery while tmpfs is full, and separation between two instances. A deployment whose command execution or output capture breaks when the business tmpfs fills fails the native tmpfs probe. When both flags are enabled and pass individually, they also test the combination. Probe instances are tracked for cleanup. Passing mocks is not production acceptance evidence.

## Task configuration

```yaml
services:
  main:
    image: registry.example/app:version
    user: "1000:1000"
    read_only: true
    mem_limit: 512m
    tmpfs:
      - /tmp:size=64m,mode=1777
      - /cache:size=32m,mode=0750,uid=1000,gid=1000
    volumes:
      - results:/results
volumes:
  results: {}
```

Service `read_only` protects the root filesystem, including against ordinary root writes. A volume's `read_only` protects only that mount. Writable volumes and tmpfs remain writable according to their own permissions. Programs writing to undeclared image paths will fail; Flotilla does not automatically open `/tmp` or modify the task's environment.

Short tmpfs syntax accepts an absolute directory, optionally followed by `size`, `mode`, `uid`, and `gid` options. Long volume syntax accepts `type: tmpfs`, `target`, and `tmpfs: {size, mode}`. Use short syntax to specify UID/GID. Unsupported options (including `noexec`, `nosuid`, and read-only tmpfs) are rejected rather than dropped.

Capacity is converted from Compose byte quantities to a whole byte count; for example `64m` becomes 67108864 bytes. Permission strings are octal (`"0750"`); YAML octal integers are accepted in long syntax. Defaults are **64 MiB, mode 1777, UID 0, GID 0**. The explicit 64 MiB default is the internal platform default, not a claim to reproduce Docker's unspecified-size default.

The internal dialect enforces:

- At most eight tmpfs mounts and total declared tmpfs capacity no greater than requested sandbox memory, checked again after deployment resource defaults are resolved. The server additionally accounts for any explicitly configured `/dev/shm` allocation.
- Canonical absolute paths, with no duplicates, parent/child tmpfs overlaps, or overlap with a volume.
- No tmpfs at or overlapping `/run`, `/var/run`, `/opt/opensandbox`, `/dev`, `/proc`, `/sys`, `/sandbox-data`, `/data`, or `/var/lib/docker`. Flotilla conservatively treats the reserved directories' subtrees as reserved too.
- No overlap with Flotilla's own `/.flotilla` and `/.flotilla-runtime` paths.
- No combination of `read_only: true` and `privileged: true`.
- Native tmpfs with `privileged: true` is also rejected by Flotilla: the optional probes measure the normal runtime, so their evidence cannot authorize a different privileged runtime.

MVM, sysbox, and kata are outside the internal feature contract. Probe the exact runtime settings; an unsupported response is an error, not a fallback. Server-side validation remains authoritative for runtime selection, template inheritance, and deployment-specific limits.

tmpfs consumption counts against sandbox memory; a process can hit OOM before filling the mount. Contents last for the sandbox lifetime and disappear with the instance. They are not copied from the image, published, or shared between instances.

## Preparation and runtime storage

The platform requires tmpfs directories to exist in the image. Preparation produces a derived image that creates missing directories, preserves existing image contents, and rejects symlink components. The actual mount hides existing content. A builder, shell-capable source image and configured build target are required for this preparation.

For read-only services, single-service writable named volumes and bind mounts become real environment-owned storage mounts rather than writable image directories. Seeding, `nocopy`, and shared-reference relationships are retained.

Read-only services also receive an explicit framework mount at `/.flotilla-runtime`. It is backed by the configured shared storage, with a private subdirectory for each instance creation attempt under the environment's owned directory. It stores service logs and temporary transfer archives, is owned by the service UID/GID, and is removed after the environment's instances have been deleted. It does not consume a business tmpfs slot or its memory budget. The `/.flotilla` tools mount remains read-only. These paths and the `_runtime` trial-volume key are reserved.

Framework operations use this path directly. Commands still receive exactly their modeled environment; platform `TMPDIR` and daemon environment variables are not implicitly inherited. Applications that need `/tmp` must declare it or another appropriate writable mount.

## Wire contract and failures

In internal mode each create sends explicit `readOnlyRootFilesystem` and `tmpfsMounts`, including false/empty values for auxiliary instances. These are managed fields and cannot be overridden through `create_fields`. Each tmpfs request includes a size in bytes, a four-digit octal mode string, UID and GID.

Before business startup, a Running instance's effective configuration must match the request after normalization. Missing fields, ignored restrictions, unexpected inherited mounts or template overrides fail readiness. The instance ID is registered for cleanup before this check. If a deployment cannot clear inherited template settings with false/empty values, use direct image creation or a matching template; Flotilla does not weaken the requested policy.

HTTP 400 and 501 are non-retryable configuration/capability failures. No filesystem fields are removed, and the task cannot proceed with a writable root or disk-directory approximation.

## Migration and verification

The previous build-time empty-directory approximation of tmpfs has been removed. Existing tasks declaring tmpfs now require native support; remove the declaration only if the task intentionally no longer requires tmpfs semantics. Ordinary upstream tasks require no new configuration.

Private preparation manifests now use schema 5 and preserve both requirements. Schema 4 manifests are rejected; prepare tasks again instead of editing their schema number.

After probing, run the opt-in public API contract to cover image preparation, service logs, directory transfers, actual mount behavior and confirmed cleanup:

```sh
python -m tests.contract.filesystem --deployment deployment.toml \
  --image "$CONTRACT_IMAGE" --out artifacts/filesystem-contract.json
```

This command creates real instances and builds a derived image. Run it explicitly on a dedicated deployment; ordinary unit tests use mocks and need no sandbox credentials. Keep the resulting evidence private. Future upstream support can add a separate lifecycle mapping while reusing the task models, validation and behavioral contracts.

The contract exercises read-only rootfs alone, tmpfs alone, and both together, including a non-root service. It records the effective filesystem settings, verifies service logs and binary directory transfers, and checks that a fresh instance has no previous tmpfs contents. After closing the client it independently lists the launch's instances, uses a separate short-lived anchor to verify that the shared launch directory is absent, confirms that audit anchor's deletion, and checks removal of the local contract temporary directory. It also checks output delivery after ENOSPC and after freeing space; a failure is retained while the remaining cases run. Cleanup uncertainty or any failed check fails the contract. Use repeated `--case readonly|tmpfs|combined|nonroot` options to rerun selected cases. The non-root fixture explicitly assigns its writable results volume to the test UID; read-write mount flags do not override POSIX ownership.
