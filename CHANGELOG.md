# Changelog

All notable changes to this project are documented here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and versions follow [Semantic Versioning](https://semver.org/). Before 1.0, minor versions may contain breaking changes.

## [Unreleased]

### Added

- `flotilla.integrations.harbor:FlotillaTaskEnvironment`: harbor runs trials on flotilla again, without a fork. `harbor run --env flotilla.integrations.harbor:FlotillaTaskEnvironment --ek deployment=<module:attribute> --path <task under a declared dataset>` drives one trial per run: the agent environment resolves the task through the deployment's declared datasets, creates the `NativeAttempt`, and opens the main role; grading follows the task's own declaration (a separate verifier environment when the tests bring one, the agent environment otherwise), harbor's tests upload doubling as the handoff into grading, since staging supersedes the copy; and whichever environment ends the trial closes the attempt. One fleet per deployment runs for the whole process, closed at interpreter exit or through the new `shutdown()`. The boundaries are explicit errors rather than surprises: a task outside every declared dataset (hub and git tasks, harbor's own copies) is rejected at startup, regrades and grading in another process are rejected because the attempt's state lives in the process that opened it, preflight loads the deployment so a bad `--ek` fails before queueing, and CPU and memory overrides fold into the trial while storage, GPU, and TPU knobs are rejected (a trial sizes itself from its task's Compose). The SDK surface doc gains the module's table, checked by the surface test like the others; `import flotilla` still does not load harbor.
- `flotilla.testing.attempt`: the fake-platform harness an attempt lifecycle needs, published behind the `testing` extra. `AttemptHarness` emulates the anchor's clear-and-copy staging and the grading command (asserting the handoff content the way a real verifier would), `prepared_source` and `write_task` publish a task with hidden tests on the fake shared tree — as a separate verifier, a shared one, or no grading contract at all — and `VERIFY_COMMAND` names the grading command a `tests/` directory derives. The lifecycle tests carried this as private scaffolding; a downstream testing its own episode loop needs the same doubles, and `flotilla.testing` is where those already live. An attempt is driven through the real `verify`, or through the three phase primitives called by hand, so a consumer's own composition is testable end to end with no platform, registry, or network.
- `docs/SDK.md`: the import surface, written down. What `flotilla`, `flotilla.native` and `flotilla.testing` export and what each name is for; the stability commitments an extension can plan around before 1.0 (the tables are additive until a changelog entry says otherwise; the grading phase order; the layer graph the import contracts pin); and the error classification a retry policy needs — infrastructure failures raise (`FlotillaError` carrying `category` and `retryable`), a grading outcome is a result and never an exception, and `ExecOutcomeUnknown` is never replayed. A unit test checks both tables against the packages' `__all__`, so the doc and the surface cannot drift apart silently. Writing the table down found one gap: `CommandBusy` is now exported at the top level, like every other error type a consumer catches.
- `NativeAttempt.end_agent_phase()`, `stage_verification()` and `open_verification_role()`: the three steps of `verify`, public. A consumer that needs something between them -- an agent teardown hook, a pause, its own timeout policy around the grading command -- was previously forced into `verify`'s one composition or into reaching past the API. The steps enforce the same order and run-once gates `verify` does: staging requires the agent phase to have ended (the hidden tests stay hidden from a sandbox the agent can still reach), opening the verification role requires staging, and `open` refuses new role opens once the agent phase has ended (an environment handle already held stays usable, since the class can only refuse what goes through it). Two behaviors moved to their step: releasing `main` when grading uses a separate verifier now happens at the phase boundary instead of inside `verify`, and the "cannot reopen main after verifier handoff" check became the phase gate with a clearer message. `verify` remains the default composition, unchanged in effect.
- `[platform]`: the platform properties a request cannot discover, declared once per deployment. `list_visibility_s` (how long a listing may lag), `max_ttl_s` (the largest TTL it grants, if it caps them), `max_label_value_len`, `link_max_members`, `implicit_egress` and `cluster_dns`. These are the values where being wrong refuses nothing and misbehaves later -- a listing budget below the truth lets GC collect a live launch, a TTL cap above it lets a sandbox expire mid-trial -- so they are stated rather than assumed or measured. `reaper.grace + platform.list_visibility_s < reaper.gc_window` and `reaper.anchor_ttl <= platform.max_ttl_s` are now checked when the config loads, not against a report at startup.
- `flotilla.compose.plan_task.plan_task`, which resolves a task directory into a `TrialPlan` in one call, and is now the only way a task becomes a trial. `TaskSource` carries where the task's files are on the client and the key the platform mounts them by, so the two filesystems never have to agree on a path and the task never has to be copied to make them. Planning belongs to the offline half of the library, so the entry points are `FlotillaConfig.plan_for(task, source, configs)` — the one place a task directory becomes a plan, which `flotilla inspect`, `NativeAttempt.resolve` and every other planner lands on — and, for a consumer, `Deployment.plan(source)` and `Deployment.plan_environment(task, source, options)`, which read the directory and fold what one run decides into the plan. `Deployment.image_configs` is the cache those resolutions share. The client's `open` and `environment` take only the plan, so the runtime imports no Compose code and planning stays something a caller can do before any client exists.
- `flotilla.native.Dataset`: a directory of task directories. `tasks()` lists the keys under it, and `source(key)` names one task on both sides at once. `[datasets.<name>]` declares one in the deployment and `resolve_datasets()` resolves them against the storage roots they live on; `launches/` and `share/` are refused as dataset roots, since those are flotilla's own state.
- `Flotilla.with_options` / `with_resources` apply what a single run decides — resource overrides, external and workspace mounts — to a plan that was resolved without them, so a caller may resolve a plan once and run it several times.
- `flotilla.registry.ImageConfigs` reads image configs straight from a registry over HTTP, by digest, two small requests per image and no layers. It replaces `docker buildx imagetools inspect`, which needed a working Docker installation to read a few kilobytes of JSON. Only `repo@sha256:...` is accepted, so a cached entry can never go stale and two services naming one tag cannot land on different images within a run; configs are cached in memory and, with `store=`, on disk with no expiry. The token realm comes from the registry's own `WWW-Authenticate` challenge rather than a conventional path, since a registry may delegate to another host and its own `/service/token` can answer every request with an anonymous token that fails on the next read.
- `flotilla.inspect`: checking a dataset without creating anything. `inspect_source(cfg, source, configs)` plans one task and returns a `TaskReport` rather than raising, so one malformed task does not hide the rest of a dataset; `sources_of(cfg, targets)` resolves what to check, from a declared dataset name, a local task directory, or every declared dataset when given nothing. `flotilla inspect` is the same thing as a command for a submit script that holds no client: it names only the tasks that would not open, prints how many of how many would, and exits nonzero if any failed. A dataset named by path is planned with no platform key, since a dataset not declared yet has none, and its plan's storage rules therefore go unchecked.
- `Deployment.management_anchor()`: a temporary Anchor for shared-storage work outside a run, which is what publishing or verifying a share release needs. It is bounded management capabilities rather than a client, and creates no `launches/<id>` directory, so it never becomes a gc candidate.
- `flotilla.compose.verification.verification_of` / `artifacts_of` compute what grades an attempt and which agent directory it reads, from the task's own `task.toml`.
- `ResourceDefaults.for_services` resolves the effective allocation from what each service declares, without a manifest in between.
- Compose `extra_hosts`, `links` and `volumes_from`. Each was rejected as unimplemented while the model already had the thing it needs. `extra_hosts` takes literal IPv4/IPv6 addresses in mapping or `name:address` list form and writes them into the `/etc/hosts` block flotilla already generates for peer names; `host-gateway` is rejected at the value level (`no-model`), since a sandbox has no host to reach, and reachability still follows the egress policy. `links` publishes `service:alias` as an alias of the target on a network both are on, attaching both to `default` when they share none, as Compose does; unlike Docker the alias is visible to every member of that network. `volumes_from` adds the donor's declared mounts to this service with `:ro` folded in, does not follow the donor's own `volumes_from`, and rejects a target this service already mounts instead of silently replacing it.
- Top-level Compose `x-*` extension fields are recorded instead of rejected. YAML anchors are resolved while loading, so a surviving `x-` key is leftover metadata; Compose strips the service-, network- and volume-level extension fields itself, so only the top level needed this.
- Compose `devices: /dev/fuse`, alongside the existing `/dev/kvm` and `/dev/net/tun`. The service runs on the privileged runtime with the `fuse` extension written per instance; a runtime that cannot host the device refuses the create request carrying it. **Breaking for deployments that set `fuse` in a static extensions table**: like `kvm` and `tun`, that key is now rejected there, because flotilla writes it per instance. The platform asks for no special runtime for FUSE, but only the privileged create path carries the extension, so a task declaring it runs privileged too.

### Changed

- **The import contracts now pin the layer graph the code actually has.** Six contracts described a graph the vocabulary move and the planning move have since changed, and a contract that no longer matches the code either passes vacuously or gets deleted when it should have been tightened. New contracts: `flotilla.models` imports no internal package (it is the bottom of the graph, which is what every layer depending on it means); `compose` imports only models and leaf utilities — no platform, runtime, native, config, or consumer package, so task resolution stays offline and stateless; the runtime imports neither `compose` nor `native` directly (config plans lazily between them, so that contract checks direct imports only); `native` imports neither `platform` nor `core` directly — everything platform-side goes through the runtime's manager and everything shared through models. `core`'s allowlist gains `native`, and `native` joins the packages that must not import the consumer surface (`integrations`, `cli`, `probe`, `testing`, `deployment`). Each new contract was verified to fail on a deliberate violation, so none of them is vacuous.
- **Breaking: the shared vocabulary lives in `flotilla.models`, and the deep import paths moved.** The value objects and pure functions that cross layer boundaries were defined inside the implementation packages that happened to write them first, which is what let `runtime` import `native` (`workspace` read `native.models.relative_path` and `native.dataset.RESERVED`) and `compose` import `native` (`verification` read `native.models.Artifact`) — the import graph had cycles, and the import-linter contracts could not be tightened over a graph like that. `flotilla.models` is now the bottom of the graph: it imports no flotilla package and contains no behavior, so every layer may depend on it. Moved: `flotilla.core.plan` (`TaskSource`, `TrialPlan`, `Unit`, `Mount`, `Network`, `Dependency`, `TrialVolume`, `Healthcheck`, `ExecContext`) is `flotilla.models.plan`; `flotilla.native.models` split into `flotilla.models.verification` (`Model`, `Artifact`, `Verification`, `check_against_plans`) and `flotilla.models.paths` (`relative_path`, `absolute_path`); `flotilla.platform.filesystem` (mount math, `TmpfsMount`, `FilesystemLimits`, `memory_bytes`, `validate_mounts`, ...) is `flotilla.models.filesystem`; the value objects and error types that `flotilla.platform.base` defined (`Resources`, `SharedVolume`, `StorageRoot`, `ExternalPolicy`, `InstanceSpec`, `ProcessSpec`, `Topology`, `InstanceHandle`, `InstanceState`, `ExecAttempt`, `ExecResult`, `ProcessStatus`, `ErrorCategory`, `FlotillaError`, `CommandBusy`, `ExecOutcomeUnknown`, ...) are `flotilla.models.platform`; the reserved dataset keys are `flotilla.models.dataset.RESERVED`. `flotilla.platform.base` keeps the `Platform` and `Clock` protocols and the `Capabilities` report and re-exports everything a backend needs, so backend plugins importing from it are unaffected, and the top-level `flotilla` import surface is unchanged; only deep `flotilla.core.plan` / `flotilla.native.models` / `flotilla.platform.filesystem` import paths break.
- **Breaking: `flotilla.integrations.harbor_source.task_environments` is `flotilla.compose.harbor_source.task_environments`.** Harbor environment selection is offline task resolution — it reads a task's `task.toml` and Compose files and produces environment definitions — so it belongs in `compose`, not in `integrations`, whose remaining member is the stock-Harbor view adapter. `flotilla.native` imported it from `integrations`, which made the attempt layer depend on an integration package.
- Harbor comes from its PyPI release (`harbor>=0.26.0,<0.27`) instead of a pinned fork commit.
- **Breaking: a deployment is a `FlotillaConfig` a caller constructs, and `deployment.toml` is gone.** The spec a recipe already holds in Python was being written to a file so another part of the same program could parse it back. `FlotillaConfig.load` no longer reads TOML or JSON: it imports `package.module:attribute` -- the spec itself, or a function returning one. That is what a separate process needs, and the only thing it needs, since `flotilla gc` exists precisely because a crashed launch leaves nobody to call the SDK, and it has to reach the deployment that crashed. Importing is as trusted as the recipe holding the spec. Every command takes `--deployment package.module:attribute`, as do `Deployment.load` and `Flotilla(deployment=...)`. `deployments/examples/opensandbox.toml` is now `opensandbox.py`, and `flotilla.testing.config.importable(spec)` publishes a spec as an import target for tests.
- **Breaking: a client-side path in a spec must be absolute** (`datasets.<name>.local_root`, `agent_runtime.layers.<name>.local_root`). A relative one used to resolve against the deployment file's directory. With no file there is no such anchor, and resolving against the working directory would make one spec mean different things in the client, a Harbor worker and `flotilla gc`. The error names the field.
- **Breaking: `flotilla probe` measures isolation and nothing else, and writes no report.** A functional capability announces its own absence: ask for a device the platform has no runtime for, a TTL beyond its limit, or a tmpfs it cannot mount, and the create request fails. Measuring those first bought a nicer error message for the price of a report format to keep. Isolation is the opposite -- a deployment that ignores an egress policy, mounts storage a sandbox never asked for, or serves the exec channel without checking the token returns success anyway -- so that is what is measured, and the only reason anything is. `probe()` returns an `IsolationEvidence`: seven properties (`external_none`, `network_acceptance`, `inbound_isolation`, `read_only`, `subdir_isolation`, `no_auto_mount`, `exec_auth`), their privileged-runtime counterparts, and what was observed for each. `flotilla probe` prints them and exits nonzero when one did not hold and `security.accept_insecure` does not name it, or when cleanup was not confirmed; `--out` is gone with the file it wrote. Everything else a deployment can be asked for is assumed available, and `Backend.capabilities` narrows it for what the configuration rules out.
- **Breaking: the isolation gate is the probe's exit status, not a client startup check.** The evidence is values in memory for the length of the probe run, and a client in another process cannot re-derive them, so `FlotillaConfig.check_isolation` runs where the probe runs. A deployment with an unwaived gap fails there; a client no longer re-reads a report and re-decides. `EnvironmentInfo.security_gaps` is gone for the same reason -- a running environment can report what the deployment accepted (`accepted_security_gaps`) but cannot claim the rest were verified here.
- **Breaking: `harbor` is a required dependency, not the `harbor` extra.** A task's `task.toml` is Harbor's format, and how a task declares a separate verifier environment -- the mode inheritance, and the image precedence between a step's verifier image, the task's, a `Dockerfile` or `docker-compose.yaml` under `tests/`, and the task's own environment image -- is Harbor's definition. Flotilla used to need it only on the preparation host, so it was optional; running a task needs it now. The `harbor` extra is gone (`pip install '.[harbor]'` becomes `pip install .`), and the deferred imports that existed to keep it out of module import are ordinary top-level imports.
- **Breaking: flotilla reads Compose itself and no longer runs `docker compose config`.** `flotilla.compose.parse.load_project` does YAML load, interpolation, `env_file` expansion, the ordered merge of several files, and Harbor's synthetic `main` service, so a host that prepares or inspects a task needs no Compose executable. flotilla supports a subset of Compose, so it maintains that subset's agreement with Docker rather than delegating. `tests/contract/compose_differential.py` is the evidence: with `FLOTILLA_TEST_COMPOSE` and `FLOTILLA_TEST_CORPUS` it reads every task of a dataset both ways and requires the resulting `Project`s to be equal field by field, findings included, plus written cases for what a generated corpus does not contain (interpolation forms, `env_file`, `.env`, multi-file merge, short volume syntax). Three places where the dialect is deliberately stricter are pinned by a test asserting Compose accepts what flotilla refuses: a bare `$VAR` (`${VAR}` is required), and a `$` in an env file value, whether quoted or not — Compose interpolates those values in turn, against the shell environment, the keys above them in the same file, the files read before them, and the service's own `environment`, so a value can depend on what another env file said.
- An image `USER` or Compose `user` of `root`, `root:root`, `0` or `0:0` resolves to 0:0 without reading the image's `/etc/passwd` and `/etc/group`. Reading them created a container from the image, so preparation pulled every image declaring `USER root` only to learn that root is uid 0 with primary group 0.
- Every rejected Compose field carries a category saying what would have to change for it to become supported: `unimplemented` (Flotilla's own work), `platform-gap` (the sandbox API has no request surface), `no-model` (a sandbox is one container in one isolation domain, so the field has no subject), `out-of-scope` (a different job from orchestration), `unsafe`, `not-reproducible`, and `docker-internal`. The categories live in `normalize.py` and in the support table, and a test compares them key by key, as it already did for the key set. A field whose values span categories is marked `mixed` and takes the strictest one. Two reasons were wrong rather than imprecise: `extra_hosts` claimed the sandbox cannot map a name to an address, but every trial already has its `/etc/hosts` written to publish service names, so an entry naming a literal address is only unimplemented and `host-gateway` is the part with no counterpart; `security_opt` and `sysctls` each span both directions, since `no-new-privileges` and namespaced sysctls belong with `cap_drop` while unconfined seccomp or apparmor and non-namespaced sysctls remove the isolation the sandbox provides.
- Compose rejection reasons for fields the sandbox API has no counterpart for now say so, instead of "not supported yet" or "not seen in task data": `cap_drop`, `security_opt`, `ulimits`, `sysctls`, `extra_hosts`, `group_add`, `pid`, `ipc` and `network_mode: service:`/`container:`. `pids_limit`, `dns`, `dns_search`, `dns_opt`, `platform`, `memswap_limit` and `cgroup` were previously unclassified and fell through to a generic "unsupported field"; they are now listed with their reason and appear in the support table.

### Removed

- **Breaking: native `harbor run` (`flotilla.integrations.harbor_native`).** `FlotillaTaskSource`, `NativeFlotillaRuntime` and `NativeFlotillaEnvironment` let Harbor's own job runner drive Flotilla, through `task_source`, trial `runtime` and `Task.from_metadata` hooks that exist only in a fork of Harbor. Keeping them meant every install pulled that fork instead of a released Harbor. Harbor-format tasks still run through `NativeAttempt` and `Dataset`; `flotilla.integrations.harbor:FlotillaEnvironment` remains as the adapter for a stock Harbor `Trial`. `docs/Harbor_Quick_Start.md` and the `native_consumers` contract go with it.
- **Breaking: `FlotillaConfig.base_dir` and `to_mapping()`.** `base_dir` existed only to resolve a path relative to the deployment file; `to_mapping()` only to rewrite those paths absolute on the way out. Every local path is absolute now, so `model_dump(mode="json")` is the serialization and `from_mapping` its inverse.
- **Breaking: the capability report.** Gone: `capabilities.json` itself, `CapabilityReport` with `SCHEMA_VERSION` and its four-state `Item` (`passed`/`failed`/`skipped`/`error`), the `Lifecycle`, `Exec`, `Network`, `Storage` and `Runtime` sections, `SECURITY_FIELDS`, `missing_required()`, `security_gaps()`, `to_capabilities()`, `evidence_profile()` (the fingerprint binding a report to the deployment text it was measured against), `FlotillaConfig.capabilities_path` / `load_report` / `check_against`, the `capabilities` key of every backend table, and `probe.list_visibility_s` and `probe.inner_image`. The listing budget moved to `[platform]` as a declared fact; `inner_image` existed only for the Docker-in-Docker check that went with the functional items.
- **Breaking: the functional probe checks.** Gone from `probe_checks.py`: `create_get_delete`, `label_list`, `renew`, `anchor_ttl`, `trial_ttl`, `prerequisites`, `exec_identity`, `files`, `placeholder_entry`, `background`, `image_digest`, `memory_limit`, `cpu_limit`, `device`, `fuse` and the tmpfs/shm measurements. Each of them measured something that fails loudly at create or exec; the failure is the answer. `tests/contract/*` still exercise these behaviors against a real deployment, which is where a platform that accepts a request and then drops it gets caught.
- **Breaking: the release, the manifest and the prepare stage.** A task directory becomes a trial in the process that runs it, so there is no intermediate artifact and nothing flotilla writes and reads back. Gone: `flotilla.manifest` with `Manifest`, its schema number and the `_upgrade` chain; `flotilla.prepared` with `PreparedEnvironment`; `prepare/release.py`, `prepare/docker.py`, `compose/manifest_gen.py`, `runtime/planning.py`, `integrations/native_import.py`, `native/release.py` (`ReleaseWriter`, `ReleaseReader`, `ReleaseBindings`, `BoundTask`, `read_dataset`), `native/files.py`, the whole `flotilla.build` package (`driver.py`, `files.py`, `images.py`, `docker.py`, `meta.py`, with `DockerRegistry` and `DockerImageAccounts`), `flotilla.testing.build`, and the `[build]`, `[prepare]`'s `docker_command`/`export_timeout` and `[task_releases.*]` config sections. `native/models.py` keeps `Verification` and `Artifact` as in-memory dataclasses and loses `Task`, `DatasetRow` and `PROTOCOL_VERSION`. `Deployment` loses `freeze()`, `release_bindings()` and the `FROZEN_*` markers; `RowValidation` is `TaskValidation`, over `TaskSource`es rather than dataset rows. Docker is no longer needed anywhere: image configs come from the registry over HTTP, and a Compose `user:` naming a non-numeric user is refused rather than resolved by creating a container to read its `/etc/passwd`.
- **Breaking: task files are mounted where they are published, not copied.** A read-only bind group is mounted straight from the task directory the platform already has (`Mount.scope="task"`), so staging it under a launch tree is not a cheaper copy — it is a step that no longer exists. Only a bind group with a writer, or a named volume, is trial-owned storage and copied out first. `files/binds/<n>` and `file-identities.json` (which recorded uid/gid/mode because a host-side copy cannot `chown`) are gone with it. `Manager.plan` admits task files anywhere on declared storage and refuses only `launches/` and `share/`, where the old rule had to refuse the whole work root because that is where staging put them.
- **Breaking: the Compose adapter.** Gone: `compose/adapter.py` with `ComposeConfigAdapter`, `ComposeToolError` and `COMPOSE_VERSION`, the `compose_adapter` argument of `load_task` / `load_environment` / `task_environments` / `select` / `prepare` / `import_task`, the `prepare.compose_command` and `prepare.compose_version` settings, `flotilla.testing.compose` with `OfflineComposeAdapter` / `offline_task` / `offline_environments`, and `tests/contract/test_compose_official.py`. The adapter's own quirks go with it: the YAML-node input gate that had to reject `include` / `extends` / `configs` / `secrets` / `label_file` before the CLI could expand them (the parser never opens an unnamed file, so they are now ordinary findings with a field path), `--no-path-resolution`, decoding Compose's `$$` transport escaping, reading the "variable is not set" warning off stderr, and the once-per-process version check. `describe_task_resources` no longer sends `compose_command` / `compose_version` in its request. Compose's `!reset` and `!override` tags are not implemented and fail the load; nothing in the corpus uses them. The reference call to the official executable now lives in `tests/contract/official_compose.py`, used only by the differential check.
- **Breaking: named volumes no longer emulate Docker's copy-up.** Docker copies the image content under a mount target into a fresh named volume. Flotilla used to reproduce that: it read every service image during preparation, compared the extractions of all copy-enabled references, packed the winner into `files/seeds/<volume>.tar`, and had the trial `tar -xpf` it into the volume. A named volume now starts empty, and `TrialVolume.owner` declares its root identity. `volume.nocopy: true` becomes **equivalent** rather than a supported option: it asks for what already happens. Gone: `TrialVolume.seed`, `Exported.seeds`, the `ImageExport` protocol and `BuildContext.image_export`, `DockerImageExport.extract` and `extract_archive`, `Anchor.unpack`, `VolumePlan.nocopy`, `VolumeMount.nocopy`, the `image_extract` and `seed_cache_copy` metric phases with the `seed_cache_hits` count, `flotilla.testing.build.FakeExport`, and `tests/contract/docker_metadata.py`. `DockerImageExport` is now `DockerImageAccounts`: preparation still runs Docker, because a named Compose `user:` resolves through the image's `/etc/passwd` and `/etc/group`.
- **Breaking: flotilla no longer builds, adapts or publishes images.** Preparation consumes images that are already published, so it needs no builder, no push target and no registry write access. Gone: `build/builder.py`, `build/cache.py`, `build/dockerfile.py`, `build/keys.py`, `DockerBuilder`, `Registry.find`/`Registry.copy`, `resolve_images`, the `link`/`mirror`/`config-only`/`cache-hit`/`built` dispositions, `BuildContext.builder`/`.adaptations`/`.user_lookup`, `BuildOutcome.built`/`.adapted`/`.dispositions`, the `build.target`, `build.mirror_images`, `build.oci_mediatypes` and `build.attestations` settings, `--image-repo`, `--require-prebuilt-images`, and the `image_preflight`, `registry_lookup`, `registry_copy`, `user0_build_push` and `application_build_push` metric phases with the `build_cache_hits` and `config_only` counts. `flotilla.testing.build.FakeBuilder` is gone; `FakeRegistry` keeps digest resolution and image configs.
- **Breaking: Compose `build:` is rejected (`out-of-scope`).** A Harbor task without `[environment].docker_image` whose environment holds a `Dockerfile` is rejected during selection instead of being built. Publish the image first and name it. `Service.build` and the `Build` model are gone.
- **Breaking: a non-root image is rejected instead of adapted.** flotilla used to build `FROM <source digest>` / `USER 0:0` and push it, because the exec daemon is the sandbox entrypoint and needs root. It now reports the image's `USER` and refuses the task: publish the image with `USER 0:0` and declare the application identity with Compose `user`, which resolves to a numeric uid/gid. `provenance["adaptation"]` is no longer written.
- **Breaking: the legacy Harbor source-task API.** `HarborAttempt`, `HarborVerification`, the `prepare/runner.py` and `share/publish.py` entry points, the compile/restore half of `flotilla.integrations.workspace`, and the `WorkspaceStore` file operations only they used. `flotilla.integrations.workspace` keeps its metadata/describe path. Task executions enter through `NativeAttempt` with a native release binding.
- **Breaking: deferred interpolation.** `runtime/values.py`, `RuntimeExpression`, the `variables`/`resolved` parameters of `normalize()`, `harbor_overlay`, `HARBOR_VARIABLES`, and the `compose/resources.py` and `compose/units.py` re-export shims are gone. Every reference is resolved when the project is read; `normalize()` never substitutes one.
- **Breaking: runtime parameters.** `OpenOptions.runtime_params` and `RunRequest.runtime_params`. A Compose reference is resolved when the task is read, from the deployment's own table and `OpenOptions.parameters`.
- **Breaking: preparation no longer inspects tmpfs and read-only runtime mount targets in the image.** `BuildContext.validate_mount_paths`, `DockerImageExport.validate_mount_paths`, the `mount_path_inspection` metric and `FakeExport(links=...)`/`FakeExport.inspected` are gone. The check created a container per service (pulling its image) to reject a symlinked or non-directory target; the container runtime already resolves a symlinked mount target inside the container's root filesystem, as Docker does, and a regular-file target fails at sandbox creation.
- **Breaking: the CLI is `inspect`, `probe` and `gc`.** Those are the three things a deployment needs from a process that is not the one running it: check a dataset before anything is created, measure isolation, and clean up after a launch that died. Gone: `flotilla anchor build`, `flotilla share publish|verify|gc`, and `flotilla prepare` and `flotilla select` with the stage they belonged to. Each remains a function (`flotilla.anchor_build.build_anchor`, `flotilla.share.release.publish_release` / `verify_release` / `gc_releases`), called from code that already holds the spec, so a command existed only to import the spec again and print what the function returned. `AnchorBuildResult.deployment_toml`, which formatted a TOML fragment to paste into a file that no longer exists, is `anchor_pin`: the published reference to put in `reaper.anchor_image`, or `None` when nothing was published. `flotilla inspect` keeps its name and changes shape: it takes dataset names rather than paths only, plans every task instead of listing environments, and reports what would not open.
- **Breaking: `flotilla.prepare`.** The package is gone with the stage: `prepare/inspect.py` with `inspect()` and its `InspectEntry` (`flotilla.inspect` replaces both), and the `select`/`prepare` CLI plumbing around them.
- Unreachable symbols: the `Backend.profile` / `FlotillaConfig.filesystem_profile` hook chain, `compile_host_volumes` and `compile_pvc_volumes` (use `StorageSettings.compile`), `derive_dockerfile`, and `share.release.release_json`.

### Fixed

- A run's `OpenOptions` are applied to a plan the caller resolved beforehand. `open` dropped `resources`, `external_mounts` and `workspace_mounts` when it was handed a `TrialPlan` rather than a `TaskSource`, so a verifier role given its own CPU allocation silently ran at the task's.
- A verifier reads the agent's handoff directory at a declared target (`/handoff/agent`) instead of relying on the release having staged it.
- A declared named volume no service mounts is dropped instead of reserving attempt-owned storage nothing can reach. Compose drops it too, so the two paths disagreed about `Project.volumes` for a task that declares more volumes than it uses — the differential check above found it.
- An undefined Compose variable is refused. Compose substitutes a blank string and exits 0, so a task referencing `${TAG}` with no value used to run with an empty string in its place; the parser refuses the task instead. A reference with a default (`${VAR:-x}`) is unaffected.
- `flotilla inspect` reads a task exactly as a run does, so their findings and resources match. The two used different parsers and could disagree; there is now only one.

### Changed

- `[share]` is optional. Without it a deployment uses the built-in release `busybox-1.36.1-r31`, which probe and runtime start publish into the work root from the Anchor image's pinned BusyBox when missing (no network). Explicit `[share]` pins keep working.
- `[agent_runtime].layers.<name>.local_root` is optional; layers can be identified by `platform_root` alone.
- Compose fields that only change local Docker behavior are recorded instead of rejected: `init`, `logging`, `stop_signal`, `stop_grace_period`, `pull_policy`, `ports`, network `gw_priority`, bridge name/MTU/`gateway_mode` options, and `depends_on.*.restart`. `restart` `always`/`unless-stopped`/`on-failure[:N]` never restart and void the run on an exit Docker would restart. `hostname` (warning) and `container_name` become resolvable names. Harbor `storage_mb` is a selection warning.

### Added

- `flotilla.Deployment`: one consumer entry point for a deployment. `Deployment.load(path, credentials=...)` binds only the deployment's `credential_env` variable from a literal `KEY=value` file; the object provides `client()`, `release_bindings()`, `setup_budget()`, `run_timeout()`, `client_overhead()`, `dataset_peak(rows)`, `validate(rows, sandboxes=..., options=...)` (starts every role except a separate verifier, so shared-verifier tasks are exercised too), `storage_identity(root)`, and `runtime_layers()` / `runtime_options(...)` for read-only `[agent_runtime]` mounts on the agent service. Consumers no longer need to read backend tables, timeout names or storage settings.
- `FlotillaConfig.load` reads `.json` configurations (frozen copies); `flotilla.environment.read_env_file` parses a credential file without changing the process environment.
- Support caller-owned external read-only mounts via `OpenOptions.external_mounts` and `RunRequest.external_mounts`. Mounts are verified for read-only flags, non-overlapping target paths, and key hygiene, and are excluded from trial volume lifecycle management (no seeding, chowning, or cleanup deletions).
- Pluggable sandbox backends. A package registers a `flotilla.backends.Backend` subclass in the `flotilla.backends` entry-point group; a deployment selects it with `backend = "<name>"` and configures it in `[backends.<name>]`. The built-in OpenSandbox backend keeps its `[opensandbox]` table, and existing configurations are unchanged. See [Writing a backend](docs/Writing_a_Backend.md).
- Opt-in internal lifecycle support for Compose read-only root filesystems and native tmpfs, with effective-configuration verification, private framework scratch mounts, and strict upstream-compatible request defaults.
- Compose `privileged: true` (warning): the service runs on the privileged runtime and is admitted with passed privileged isolation evidence. The Docker check is now only a recorded measurement in `runtime.privileged_runtime`.
- Compose `devices` `/dev/kvm` and `/dev/net/tun` (plus `cap_add: [NET_ADMIN]` alongside TUN). Such services run on the privileged runtime with per-instance `kvm`/`tun` extensions, carried through the plan into `InstanceSpec.devices`; a runtime that cannot host the device refuses the create request. The extension keys `kvm` and `tun` are no longer accepted in static extensions tables. Trial volumes mounted writable by privileged-runtime units are opened with `chmod -R a+rwX` before creation (sysbox root does not own anchor-created storage).
- Compose `shm_size` on the internal filesystem dialect, sent per instance as the `sandbox-system.io/shm-size` extension, sharing the tmpfs memory budget, and verified per instance against the size the platform echoes before startup. Upstream OpenSandbox has no equivalent setting and rejects such tasks.

- Task-level `network_mode = "no-network"` and `allow_internet = false`, preserving service links while removing external access throughout preparation and execution.
- Explicit cluster DNS declarations: offline policies tolerate only the declared resolver IPs on TCP/UDP 53 and reject every other implicit egress exception.
- Opt-in sandbox ingress enforcement using the shared OpenSandbox lifecycle route. Compose `network_mode: none` now checks both outbound exceptions and inbound isolation; upstream requests retain the standard egress-only schema by default.
- Correlated execd request timing logs for send, response headers, command ID, and stream closure, without command contents or credentials.
- Compose `${VAR:+alt}` / `${VAR+alt}` and nested references inside defaults and alternatives, plus Harbor's `CONTEXT_DIR` interpolation variable (the environment directory).

### Changed

- `flotilla gc` finds launches from sandbox labels as well as `launches/`, and when its anchor cannot start it deletes sandboxes by label only (`GcReport.mode = "platform"`, `directories_skipped`) and exits 1. With an anchor it also removes `tasks/.staging`, `tasks/.trash` and `share/staging` entries older than `--staging-age` (default 24 h). Share release staging names now carry a timestamp.
- `CleanupRecord` gains `reason` and `error`, naming what is still unconfirmed and the last related error.
- **Breaking:** an open's budgets are split by phase. Waiting for a `trial_concurrency` / `instance_budget` slot is bounded by `OpenOptions.admission_timeout` (default `limits.admission_timeout`, 3600 s) and raises the new `AdmissionTimeout` (a `TimeoutError`) with the current counts. `startup_timeout` now starts at admission, so queueing no longer consumes it. Client start (anchor and share check) is bounded by the new `timeouts.client_start` (300 s) instead of `timeouts.prepare`.
- The share check at client start downloads only `RELEASE.json`, compares its sha256 and confirms `bin/busybox`. Per-file verification stays in `flotilla share verify`.
- `flotilla probe`, `gc`, and `share` construct their platform through the same factory as the runtime, so `opensandbox.privileged_extensions` now also applies to privileged instances these commands create.
- tmpfs now requires native support; the previous empty-directory approximation is removed without fallback. Private preparation manifests use schema 5 and must be regenerated.

### Fixed

- Recover transient or unknown transport responses for read-only anchor `stat` within five attempts and a 30-second retry-admission window. Preserve metadata results during recovery without replaying their helper, writes or workloads; retain existing bounded HTTP download retries without adding an outer retry layer.
- Recover bounded native Harbor metadata reads after `ESTALE`, using fresh parsing and a shared request wait budget without replaying copies, Compose/build commands or workloads. Surface tree-enumeration errors instead of silently validating incomplete trees; preserve all-or-nothing metadata publication and original failures on exhaustion.
- Healthchecks propagate non-retryable execution errors, including unknown outcomes, instead of running another check and potentially declaring the environment healthy. Public foreground/background calls preserve environments after an explicit `CommandBusy` rejection.
- Services with both `service_healthy` and `service_completed_successfully` dependents now drive both conditions independently.
- A sandbox no longer expires while its environment is still starting. Sandboxes are renewed only once the environment is ready, but they were created with `reaper.trial_ttl` (1800 s by default), so an open whose startup ran past that TTL (for example `startup_timeout` above 1800 s, or long health checks) had its sandboxes reclaimed by the platform mid-start and failed with "instance vanished during start". Each sandbox is now created with at least the open's startup budget plus `reaper.renew_before_s`.
- Environment variable names that are not shell identifiers but that Docker accepts (for example `discovery.type` or `APT::Get::AllowUnauthenticated`) are no longer rejected. The OpenSandbox exec wrapper passes them to execd under internal `FLOTILLA_ENV_<n>` aliases and restores the original names when it clears the environment. Values still travel only in the request `envs`. Names that are empty, contain `=` or NUL, start with `-`, or start with `FLOTILLA_ENV_` are still rejected.
- A sandbox the platform never starts no longer holds its trial and quota for the whole `timeouts.create` budget. After `timeouts.pending` (new, default 300 s) it is deleted and created again once, through the existing recreate path; a second stall fails the open.
- Commands waiting for a free HTTP connection are no longer counted as sent and no longer run down their timeout while they wait. Previously a burst of internal commands (for example every environment's health check at once) queued inside the 100-connection pool, expired there, and was reported as an unknown outcome, so healthy environments were marked lost. Requests now wait in Flotilla for one of `opensandbox.max_connections` (new, default 100) connections per pool.
- A create request whose response was lost no longer holds its trial for the whole `timeouts.create` budget. The request now has its own `timeouts.create_request` (default 60 s), after which the sandbox is found by its labels and adopted; previously the request timeout equalled the stage timeout, so this recovery could never run.
- Retry confirmed timeouts of the internal no-op health probe within the existing check budget instead of immediately losing the environment; user commands are never replayed.
- Treat execd command-stream `409 CONFLICT` responses as explicit `CommandBusy` rejections: healthchecks skip that round, foreground and background calls preserve the rejection, and commands are never automatically replayed. Other conflicts retain their existing classification.
- Send each sandbox's execd access token when replacing its network policy. Upstream OpenSandbox's Docker runtime serves `PUT /sandboxes/{id}/networkpolicy` through execd's proxy and rejected the unauthenticated request with HTTP 401, so linking multi-service environments failed.
- Stop doubling line terminators in command output from execd 1.1.1 and later, which keeps each line's terminator in stdout/stderr events.

## [0.1.1] - 2026-10-20

Initial public release plus downstream orchestration contracts.

### Added

- Async Python API (`Flotilla`, `open_task`, `open_environment`, `environment`) for running a Compose task as one sandbox per service, with confirmed cleanup reports.
- Command execution with explicit argv, identity, and environment; background processes; binary file and directory transfers.
- Cancellation and timeout semantics that never replay commands and report unknown outcomes as `ExecOutcomeUnknown`.
- Automatic image preparation with Docker BuildKit, including digest resolution, mirroring, and derived images.
- Explicit network policies (`none`, allowlist, `any`) with CIDR or sandbox-ID peer links.
- OpenSandbox backend supporting the `current` and `legacy` execd protocols.
- CLI: `inspect`, `probe`, `gc`, and `share publish|verify|gc`.
- Optional Harbor 0.24.0 environment adapter (`flotilla.integrations.harbor:FlotillaEnvironment`).

- Environment-specific inspection and public resource reservations, including per-client anchor overhead.
- Process waits with bounded observation timeouts, and explicit stop with confirmed termination.
- Public `flotilla.testing` helpers for downstream contract tests, separate from runtime imports.
